# Smart Money Tracker

Личный инструмент для одного пользователя: что делают отслеживаемые
инвесторы (13F) → пересекается ли это с моим watchlist/портфелем → что
происходит с моими деньгами. Не продукт, без аккаунтов, без монетизации —
подробные границы см. в описании задачи / истории обсуждения проекта.

Живёт как отдельная папка внутри `Tik-tok` (репозиторий изначально заведён
под другой личный проект — соцсети — но это тот же принцип: личные
инструменты Алексиса, не связанные продукты).

### CUSIP → ticker: закрыт открытый вопрос из спеки

Спека помечала security master как открытый вопрос ("резолвить вручную,
не строить общий маппинг"). По факту решать не пришлось: edgartools несёт
с собой offline-таблицу CUSIP→Ticker (`cusip_ticker_mapping()`,
источник — проект `edgar-storage` того же автора) и использует её сама
внутри парсера 13F (`edgar/thirteenf/parsers/infotable_xml.py`). Она
покрывает основные акции, работает без сети и без своего ключа — то, что
нужно для 20-40 тикеров MVP. Что не резолвится — остаётся `NULL` в колонке
`ticker`, руками разбираем по мере необходимости, отдельный security-master
слой не строим.

### Ограничение текущей песочницы: data.sec.gov недоступен

`scripts/fetch_13f.py` не смог быть прогнан live здесь — исходящий трафик
на `data.sec.gov` блокируется политикой этого облачного окружения (403 от
gateway, не ошибка кода/ключа/CUSIP). Тот же паттерн уже был в этом
репозитории для Edge TTS, см. `../RUN_LOCALLY.md`.

Код и API-использование проверены по исходникам edgartools (структура
`ThirteenF.holdings`, `report_period`, `is_amendment` и т.д.) и офлайн-тестами
выше; сам HTTP-вызов к EDGAR не проверен end-to-end. Прогнать на машине с
обычным интернетом:

```bash
cd smart_money_tracker
pip install -r requirements.txt
cp .env.example .env   # вписать EDGAR_IDENTITY = "Имя email@example.com"
python3 scripts/fetch_13f.py
```

Если после первого live-прогона парсинг/маппинг разойдётся с ожиданиями —
это шаг 1 ещё не закрыт, разбираемся до перехода к шагу 2.

Готово на шаге 2:
- `compare.py` — сравнивает holdings текущего периода с предыдущим по CUSIP:
  `NEW` (не было — появилось), `ADD`/`REDUCE` (изменилось число shares, с
  `pct_change`), `HOLD` (не изменилось), `EXIT` (было — пропало). Никакого
  скоринга/порогов "значимости" — только факт и сырой процент, как в границах
  проекта.
- `scripts/compare_quarters.py` — пересчитывает историю для всех инвесторов
  из `investors.py` по уже загруженным filings (сам данные не тянет).
- `tests/test_compare_quarters.py` — **прошли**, оффлайн (чистая работа с
  БД, сеть не нужна): NEW/ADD/REDUCE/HOLD/EXIT на одном переходе периодов,
  что EXIT не повторяется на следующий квартал после ухода позиции, и что
  повторный запуск сравнения идемпотентен (не плодит дублирующиеся EXIT-строки).

### Как fetch и compare сочетаются

`scripts/fetch_13f.py` только тянет и сохраняет holdings текущего filing
(`status`/`pct_change` = `NULL`). `scripts/compare_quarters.py` затем
проставляет статусы, сравнивая с предыдущим периодом того же инвестора, и
добавляет EXIT-заглушки (13F не репортит нулевые позиции, поэтому "ушедшая"
позиция иначе была бы просто не видна). Порядок для нового квартала:
`fetch_13f.py`, затем `compare_quarters.py`.

### Amendments: как на самом деле решено, не через `amendment_of`

Спека предупреждала: `13F-HR/A` может переопределять более раннюю версию за
тот же период, и без учёта этого сравнение даст ложные NEW/EXIT. Схема несёт
колонку `filings.amendment_of` под это, но она осталась `NULL` — вместо
явной FK-цепочки "amendment ссылается на оригинал" `get_effective_filings()`
в `db.py` берёт **последний по `filed_date` filing на period** как
единственный "действующий" для этого квартала (амендмент почти всегда подан
позже оригинала, так что `MAX(filed_date)` естественно выбирает его). Проще,
чем резолвить цепочку amendment_of при инсёрте, и даёт тот же результат для
сравнения кварталов. Если позже понадобится сам факт "это была правка" (не
только "какая версия действующая") — тогда `amendment_of` и пригодится,
пока не используется.

Готово на шаге 3:
- `watchlist.py` + `scripts/watchlist_cli.py` — add/remove/list тикеров,
  без сделок, без обязательной цены (add/remove/list прямо по спеке). Дедуп
  по `(ticker, list_name)`, тикер регистронезависим.
- `portfolio.py` + `scripts/portfolio_cli.py` — ручной ввод buy/sell,
  `compute_positions()` считает shares_held / average cost / invested методом
  weighted average (не FIFO/LIFO — проще, достаточно для личного трекера).
  Полностью закрытые позиции не показываются как открытые. Продажа больше,
  чем есть в позиции, — это ошибка ввода, а не отрицательная позиция:
  `compute_positions()` явно падает с понятным сообщением, какой тикер и на
  какую дату не сходится.
- `tests/test_watchlist_portfolio.py` — **прошли**, полностью офлайн (у
  portfolio вообще нет сетевого кода на этом шаге): дедуп watchlist,
  weighted average cost после buy/buy/partial-sell, закрытая позиция не
  висит в выводе, overselling кидает понятную ошибку.

**Чего в шаге 3 намеренно нет**: unrealized P/L и return % — по спеке они
считаются от текущей цены, а источник цен (Alpha Vantage vs yfinance — один
основной, второй fallback, не дёргать оба) ещё не выбран. Это осознанно
отдельное решение, а не забытая часть — трогать его нужно явно, когда решим,
на чём останавливаемся (5 запросов/мин + 25/день у Alpha Vantage против
безключевого, но неофициального yfinance).

## Известные ограничения (не забыть на будущих шагах)

- 13F ≠ весь портфель: только US-листингованный long equity, AUM >$100M,
  без шортов/опционов/бондов/кэша/международных активов, часть holdings
  может быть скрыта (confidential treatment).
- Amendments (`13F-HR/A`) могут переопределять более раннюю версию за тот
  же период — решено через `get_effective_filings()` (см. выше), не через
  `amendment_of`. Не переоткрывать эту проблему на будущих шагах не проверив
  сначала, решает ли она её достаточно (пока проверено только офлайн-тестами
  на синтетических данных, не на реальной паре amendment/original).
- Rate limits: 13F обновляется раз в квартал, чаще опрашивать бессмысленно.
- Источник цен для watchlist/portfolio не выбран (см. выше) — до выбора
  unrealized P/L, return % и любая цена в watchlist недоступны.
- Живой прогон `fetch_13f.py` против настоящего data.sec.gov ещё не сделан
  ни разу за весь проект (см. статус шага 1 выше) — приоритет перед тем, как
  строить шаг 4 (overlap) поверх непроверенных живых данных.
