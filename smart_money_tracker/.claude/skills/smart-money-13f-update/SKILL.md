# Smart Money 13F Update

Операционный скилл для `smart_money_tracker/` — личного трекера 13F/watchlist/
portfolio (не продукт, один пользователь, см. `README.md` в корне проекта).
Он покрывает то, что уже реально существует в коде: загрузку последнего
13F-HR через EdgarTools (`scripts/fetch_13f.py`), сравнение с прошлым
кварталом — NEW/ADD/REDUCE/EXIT/HOLD (`scripts/compare_quarters.py`) — и
список отслеживаемых инвесторов (`investors.py`). Watchlist, portfolio и
overlap-экран — следующие шаги roadmap, их в коде ещё нет, не выдумывай для
них workflow.

## Зачем нужны проверки, а не просто "запустить скрипт"

13F обновляется раз в квартал и задерживается на 45 дней — ошибку заметишь
не сразу, если просто доверять коду без результата на экране. Скрипт уже
печатает статус по каждому инвестору, но эти строки легко проглядеть в потоке
вывода. Задача скилла — прочитать их осмысленно и сказать прямо, что прошло
нормально, а что нет, а не пересказать вывод скрипта.

## Шаг 1: проверить EDGAR_IDENTITY

SEC EDGAR отклоняет запросы без identity вида `"Имя email@example.com"`.
Проверь `smart_money_tracker/.env` (или переменную окружения `EDGAR_IDENTITY`).
Если её нет — скрипт сам откажется работать и подскажет формат; не пытайся
обойти это заглушкой, просто попроси пользователя вписать identity в `.env`
(см. `.env.example`).

## Шаг 2: запустить обновление

```bash
cd smart_money_tracker
python3 scripts/fetch_13f.py
```

Скрипт идёт по каждому инвестору из `investors.py`, тянет последний
13F-HR/13F-HR-A, парсит holdings и пишет в SQLite (`data/smart_money.db`).
Один прогон обычно занимает секунды-десятки секунд на 5-10 инвесторов — сеть
до `data.sec.gov`, а не тяжёлые вычисления, main bottleneck.

**Известное ограничение окружения**: если это выполняется в песочнице с
ограниченным исходящим трафиком (например, некоторые облачные dev-сессии),
`data.sec.gov` может быть заблокирован на уровне сети — тогда каждая строка
даст `403 Forbidden`. Это не баг кода и не повод чинить CUSIP/CIK — просто
сообщи пользователю, что нужно прогнать на машине с обычным интернетом
(см. `README.md` в корне проекта, раздел про ограничение песочницы).

## Шаг 3: пересчитать статусы кварталов

```bash
python3 scripts/compare_quarters.py
```

Это отдельный скрипт от `fetch_13f.py` намеренно — он ничего не тянет из
сети, только сравнивает уже загруженные periods в БД. Запускай его сразу
после `fetch_13f.py` при обычном квартальном обновлении. Если у инвестора
в БД меньше двух periods (первая загрузка), скрипт честно скажет "сравнивать
не с чем" — это не ошибка.

## Шаг 4: прочитать вывод осмысленно

Каждая строка — одна из трёх форм:

- `  ok <Имя> (<Фонд>): <accession_no>, период <YYYY-MM-DD>, N holdings, R/N с тикером`
  — успех. Проверь на глаз:
  - **N holdings равно 0** — подозрительно для крупного фонда (Berkshire,
    Bridgewater и т.п. держат десятки-сотни позиций). Скорее всего проблема
    в парсинге инфотейбла, а не в том, что у фонда правда нет holdings — стоит
    перепроверить сам filing (accession_no) на EDGAR вручную, а не списывать
    на "у фонда пусто".
  - **R/N (доля с резолвленным тикером) заметно ниже 50-60%** — тоже стоит
    присмотреться. Offline CUSIP->ticker таблица edgartools покрывает
    основные US-акции, так что у обычного equity-портфеля большая часть
    CUSIP должна резолвиться; низкая доля чаще говорит о проблеме с версией
    таблицы или о фонде с необычной структурой holdings, чем о "так и должно
    быть". Не подавляй это молча — скажи пользователю цифру и что она
    низкая.
- `  ! <Имя>: нет 13F-HR filings для CIK <CIK>` — CIK, скорее всего, неверный
  или это не 13F-филер вовсе. Не проверяй заново автоматически — вернись к
  пользователю с этим CIK, чтобы он подтвердил/поправил.
- `  ! <Имя>: ошибка — <текст>` — если текст `403 Forbidden` и похоже на
  сетевую блокировку (а не auth/rate-limit от самого SEC), это, вероятно,
  ограничение песочницы (см. шаг 2) — скажи об этом прямо, не пытайся
  повторять запрос в цикле.

`compare_quarters.py` печатает свои строки в похожем формате:

- `  ok <Имя>: <период1> -> <период2> — NEW n, ADD n, REDUCE n, HOLD n, EXIT n`
  — успешное сравнение. Если NEW+EXIT подозрительно большие относительно
  общего числа holdings (скажем, больше половины портфеля поменялось за
  квартал у фонда, который обычно держит долгосрочные позиции) — не
  списывай на "так бывает", вероятно расхождение CUSIP между кварталами
  (например, сплит акций сменил CUSIP) — стоит явно отметить пользователю,
  а не тихо пропустить.
- `  - <Имя>: меньше двух periods в БД, сравнивать не с чем` — нормально для
  первой загрузки инвестора, не ошибка.
- `  ! <Имя>: ещё не загружался, сначала scripts/fetch_13f.py` — забыли
  прогнать fetch перед compare, просто запусти fetch и повтори.

После прогона кратко резюмируй пользователю: сколько инвесторов ok на fetch
и на compare, сколько с проблемами, и для проблемных — что именно не так (а
не просто "3 из 5 прошли").

## Добавление нового инвестора

Открой `investors.py` и добавь запись в список `INVESTORS`:

```python
{"name": "<Имя управляющего>", "fund": "<Юридическое название фонда>", "cik": "<10-значный CIK с ведущими нулями>"},
```

Как найти CIK:

1. Сначала проверь offline-датасет, который уже в edgartools — он покрывает
   основные крупные фонды и не требует сети:
   ```python
   import json
   data = json.load(open("<путь до пакета edgartools>/reference/data/portfolio_managers.json"))
   # data["managers"] — словарь по company_key, у каждого есть "cik" и "match_patterns"
   ```
   (путь можно получить через `python3 -c "import edgar, os; print(os.path.dirname(edgar.__file__))"`)
2. Если фонда там нет — нужен реальный сетевой поиск на EDGAR (полнотекстовый
   поиск по названию фонда или `Company` lookup в edgartools). Это требует
   доступа к `data.sec.gov`/`www.sec.gov` — если сеть недоступна в текущем
   окружении, попроси пользователя дать CIK самому или прогнать поиск там,
   где сеть есть. Не угадывай CIK по памяти и не придумывай его — неверный
   CIK молча даст "нет filings" или, хуже, данные другого фонда.

После добавления — прогони `scripts/fetch_13f.py` ещё раз и проверь, что
новый инвестор дал `ok` со вменяемым числом holdings (шаг 4). Сравнение
кварталов появится само на следующий раз, когда для этого инвестора в БД
накопится второй period — раньше сравнивать не с чем.

## Чего этот скилл не делает

Не пытайся достроить недостающие шаги roadmap по ходу дела:

- Watchlist, portfolio, overlap-экран — таблицы `watchlist` и
  `portfolio_transactions` в `schema.sql` есть, кода под них нет вообще.

Если пользователь просит что-то из этого — это уже не "обновление 13F",
а следующий шаг проекта; не подменяй его наспех написанным кодом внутри
этого скилла.
